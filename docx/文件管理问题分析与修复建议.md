## 1. 范围与验证说明

本文记录已发现的文件管理缺陷、现有流程缺口和需要进一步验证的风险。产品功能扩展与架构优化见 [项目优化方向与实施路线](项目优化方向与实施路线.md)。

当前已有多文件导入、打开目录、目录懒加载、重命名、磁盘删除、复制路径、资源管理器定位、未保存标记、退出确认、当前文件外部修改检测，以及“重载／覆盖”操作。以下问题是在这些已有能力基础上发现的，不应理解为相关功能全部缺失。

验证方式：

- **隔离验证**：执行现有 `editor-store.ts` 的状态逻辑，模拟 Tauri API 和提示组件，检查状态变化与调用参数。没有对真实文件执行写入、移动或删除。
- **静态确认**：根据前后端源码和调用关系确认实现情况，未进行完整桌面端交互复现。
- **待交互验证**：源码存在明确风险路径，但具体时序或运行结果仍需在 Tauri 中验证。
- 当前工作树包含尚未提交的文件管理改动，部分问题已经得到首层修复，本文会区分“已部分修复”和“仍未闭环”。
- 本次复核执行 `npm run build` 未通过：`moveNode` 的返回类型与实现不一致，`saveFileById` 中还有未使用变量。构建必须先恢复绿色，后续验证结果才可作为实施基线。

优先级定义：

- **P0**：可能损坏文件或造成未保存内容丢失，应先修复。
- **P1**：核心文件操作、身份一致性或保护机制不完整。
- **P2**：交互完整性、便利性或边界场景问题。

## 3. 问题、原因与解决方法

### F01：PDF 可进入文本保存流程

**问题**：历史流程中打开 PDF 后，全局 `Ctrl/Cmd+S` 会进入通用保存逻辑，将预览使用的 asset URL 作为文本内容写到原 PDF 路径。当前工作树已在 `saveFile`、`saveFileAs` 和 `saveFileById` 增加能力检查，但仍需验证所有入口和 PDF 原始字节不变。

**原因**：PDF 的预览地址仍复用了文本编辑器的 `content` 字段；后端 `write_file` 仍接收任意路径和字符串，前端能力检查不能替代后端的防误用边界。

**解决方法**：

1. 为文档明确建模类型和能力，如 `kind`、`canEdit`、`canSaveText`，将 PDF 预览地址与文本缓冲区分离。
2. 在所有文本保存入口统一拒绝 PDF 等不可文本编辑文档，不能只禁用一个按钮。
3. PDF 如需“另存为”，通过二进制复制实现；文本写入服务增加针对不支持类型的防误用校验。

**验收标准**：查看 PDF 时触发快捷键、单文件保存和全部保存，都不能调用文本写入；PDF 原始字节保持不变。

**代码位置**：[保存逻辑](../src/lib/editor-store.ts) 的 `setActiveFile`、`saveFile`、`saveFileById`；[全局快捷键](../src/components/editor/index.tsx)；[磁盘写入](../src-tauri/src/lib.rs) 的 `write_file`。

### F02：保存期间的新修改被错误标记为已保存

**问题**：保存开始时内容为 A，在写入完成前继续输入得到 B。历史流程会把 A 的保存结果错误地标记为已保存。当前工作树已加入编辑版本和按文档保存队列，但需要验证另存为、逐文件保存和 WYSIWYG 提交时序。

**原因**：保存函数需要同时保护内容快照、编辑版本和保存顺序。当前队列是在前端串行化请求，尚未解决外部磁盘版本冲突，也尚未覆盖所有编辑器缓冲区。

**解决方法**：

1. 为文档增加编辑版本和已保存版本，保存时捕获文档 ID、路径、版本和内容。
2. 写入成功后，仅当当前版本等于本次保存版本时清除未保存标记，否则保留 `isDirty`。
3. 同一文档的保存请求排队或合并，避免旧请求后完成并覆盖新结果。
4. 保存结果使用明确的成功、取消、失败、冲突状态，供全部保存与退出流程使用。

**验收标准**：模拟延迟写入，保存期间继续编辑后仍显示未保存；连续保存不会回退磁盘内容。另存为、逐文件保存同样满足要求。

**代码位置**：[editor-store.ts](../src/lib/editor-store.ts) 的 `saveFile`、`saveFileAs`、`saveFileById`。

### F03：移除节点缺少未保存处理闭环，移除父目录可能留下失效选择

**问题**：“从列表中移除”目前会阻止包含未保存文件的操作，并在移除当前节点后清空选择；但没有“保存后移除／放弃修改／取消”的处理闭环。移除父目录时，仍需保证独立文档缓冲区和退出检查不会丢失子文件草稿。

**原因**：右键菜单直接调用同步的 `removeNode`；当前函数虽已递归检查后代未保存文件，但只能 toast 拒绝，不能等待保存结果，也没有区分关闭文档、关闭工作区目录和从列表解除关联。

**解决方法**：

1. 建立统一的关闭／移除流程，递归收集受影响的文档。
2. 有未保存内容时提供“保存后移除／放弃修改／取消”；保存取消或失败时中止移除。
3. 移除完成后同步当前选择、滚动记录、搜索结果等关联状态。
4. 区分“关闭工作区目录”和“关闭文档”：如果允许文档继续打开，应由独立文档缓冲区管理，不能只保留悬空 ID。

**验收标准**：移除未保存文件、含未保存子文件的目录、当前文件的父目录，均不会静默丢失内容；操作后当前文档引用始终有效或明确为空。

**代码位置**：[右键菜单](../src/components/editor/file-tree-context-menu.tsx)；[editor-store.ts](../src/lib/editor-store.ts) 的 `removeNode`、`getUnsavedFiles`。

### F04：新建文件和目录没有执行磁盘创建

**问题**：历史流程只产生内存节点。当前工作树已在真实父目录下调用 `create_file` 和 `create_directory`，并把无路径根级文件标记为新文件；根级新建目录仍没有明确的磁盘位置语义，创建与刷新之间也需要补竞态验证。

**原因**：此前 `confirmCreate` 仅更新 store。当前实现已经区分部分路径状态，但仍使用“先检查存在、再创建”的两步流程，不能防止并发重名；根级虚拟节点与真实目录节点的语义仍混合。

**解决方法**：

1. 区分“无路径草稿”和“真实目录下创建文件”。前者保留为未保存草稿，后者调用后端实际创建。
2. 将创建流程改为异步，磁盘成功后再插入或确认节点；失败时保留输入并展示原因。
3. 增加重名和名称校验；创建文件使用禁止覆盖的创建方式，避免存在性检查与创建之间的竞态。
4. 明确根级“新建文件夹”的含义：选择磁盘位置创建，或明确标注为虚拟分组，不能与真实目录混用。

**验收标准**：新建空文件、空目录后资源管理器可见，重新展开和重启后仍存在；重名不覆盖原文件；无路径草稿参与未保存检查。

**代码位置**：[editor-store.ts](../src/lib/editor-store.ts) 的 `confirmCreate`；[lib.rs](../src-tauri/src/lib.rs) 的 `create_file`、`create_directory`。

### F05：目录刷新改变已有节点 ID或丢失草稿

**问题**：历史刷新会重新生成节点 ID。当前工作树在直接路径匹配时尝试保留已有 ID、内容和版本，但如果外部删除整个父目录，包含 dirty 子孙的目录节点不会因为自身没有 dirty 标记而自动保留，仍可能丢失草稿引用。

**原因**：目录读取为每个条目创建新 ID，`mergeRefreshedChildren` 只对当前层按字符串路径匹配；文档生命周期仍依赖树节点，尚未形成独立的文档缓冲区和文件身份索引。

**解决方法**：

1. 匹配到同一文件或目录时保留原 ID、文档关联和必要 UI 状态，只更新磁盘元数据。
2. 删除条目时检查整个子树中的未保存文档；不能因目录自身没有 `isDirty` 就丢弃其子文档。
3. 将磁盘列表刷新和文档生命周期分开，刷新完成后校验当前文档仍可解析。

**验收标准**：打开并编辑文件后反复刷新父目录，ID、当前选择、草稿内容和滚动位置保持稳定；外部删除父目录不丢弃子文件草稿。

**代码位置**：[file-operations.ts](../src/lib/file-operations.ts) 的 `createNodeFromEntry`、`loadFolderChildren`；[editor-store.ts](../src/lib/editor-store.ts) 的 `mergeRefreshedChildren`、`replaceFolderChildren`。

### F06：拖拽移动未同步磁盘路径

**问题**：拖拽后文件在界面中出现在目标文件夹，但磁盘位置和 `filePath` 不变，保存仍写入旧位置。当前 `moveNode` 仍只改内存树；其类型已声明为异步但实现仍返回同步结果，当前工作树因此无法通过 TypeScript 构建。

**原因**：`moveNode` 只从内存树移除并插入节点，还会直接修改部分原节点，插入时清空 `children`，不能直接复用为完整的目录移动实现；当前 UI 主要提供文件拖动。

**解决方法**：

1. 先定义后端 `move_path` 操作，成功后再更新节点位置、路径、监听和相关索引；失败时树和源文件都保持原状。
2. 处理同名目标、目标不存在、权限失败及跨卷移动；跨卷失败不得先丢弃源文件。
3. 对草稿、虚拟分组、真实目录分别定义移动语义。
4. 使用不可变状态更新；扩展目录拖动时保留整个子树，禁止移入自身或后代。嵌套拖放需避免事件冒泡导致重复移动。

**验收标准**：移动后磁盘位置与树一致，保存写入新路径；失败时树和源文件均保留；同名文件不被静默覆盖。

**代码位置**：[file-tree.tsx](../src/components/editor/file-tree.tsx) 的 `handleDrop`；[editor-store.ts](../src/lib/editor-store.ts) 的 `moveNode`。

### F07：删除范围提示与磁盘操作范围不一致

**问题**：确认弹窗统计已加载树中的文件数，后端却删除完整磁盘目录。未展开子目录和扩展名过滤掉的图片等文件也会被删除；当前操作是永久删除，没有回收站恢复能力。

**原因**：`countFilesInNode` 只遍历内存节点，而 `delete_directory` 使用 `fs::remove_dir_all`。懒加载树不是磁盘目录的完整清单。

**解决方法**：

1. 默认使用系统回收站；永久删除作为单独且明确的操作。
2. 展示真实磁盘路径，并说明包含未显示内容。需要精确数量时由后端统计；不能完成统计时不展示误导数字。
3. 删除前统一处理受影响的未保存文档，删除成功后同步文档与树状态。

**验收标准**：包含未展开目录和图片的目录，提示与实际删除范围一致；普通删除可以从回收站恢复；失败时不提前移除节点。

**代码位置**：[file-tree-context-menu.tsx](../src/components/editor/file-tree-context-menu.tsx) 的 `countFilesInNode`；[lib.rs](../src-tauri/src/lib.rs) 的 `delete_file`、`delete_directory`。

### F08：普通保存绕过外部冲突处理

**问题**：已有外部修改提示及“重载／覆盖”入口，但普通 `Ctrl/Cmd+S` 仍可能在前端未发现变化时直接写入，未要求用户明确处理冲突。

**原因**：保存前没有核验磁盘版本，未将 `hasExternalChanges` 纳入通用保存流程；外部检查主要比较修改时间，且保存期间会临时抑制检查。

**解决方法**：

1. 保存请求携带上次读取的磁盘版本，后端提供“版本未变化才写入”的单次操作，避免前端检查与写入之间的竞态。
2. 冲突时提供查看差异、重新载入、另存副本、明确覆盖等选择。
3. 结合修改时间、大小或内容摘要识别变化，明确并测试多进程同时写入时的保护边界；原子替换本身不能解决冲突。
4. 将自身写入产生的事件与其他外部事件区分处理，避免仅依靠时间窗口漏掉变化。

**验收标准**：外部修改之后普通保存不会静默覆盖；有本地修改时重新载入需明确确认；明确覆盖后更新基准版本。

**代码位置**：[editor-store.ts](../src/lib/editor-store.ts) 的 `checkActiveFileForExternalChanges`、`saveFile`；[status-bar.tsx](../src/components/editor/status-bar.tsx)。

### F09：磁盘写入缺少原子替换

**问题**：保存直接覆盖原文件。异常中断或写入失败时存在原文件被截断、内容不完整的风险；原子替换本身也不能解决 F08 的外部冲突。

**原因**：后端使用 `fs::write`，没有临时文件、同步和替换流程。

**解决方法**：将 F08 与 F09 设计成一个后端保存协议：在同目录创建唯一临时文件，完整写入并按需要同步，同时校验期望的磁盘版本，再使用平台支持的替换方式更新目标；失败时保留原文件并清理临时文件。验证 Windows 文件占用、权限和替换语义，按产品要求保留原权限及备份。

**验收标准**：模拟写入失败、磁盘空间不足、目标被占用时，原内容仍可读取；失败不能显示保存成功，也不能清除未保存标记。

**代码位置**：[lib.rs](../src-tauri/src/lib.rs) 的 `write_file`。

### F10：WYSIWYG 延迟内容没有统一保存前提交机制

**问题**：块编辑有 300ms 防抖。用户输入后立即按保存，可能读取到尚未更新的 store 内容。当前卸载提交只在存在 timer 时触发，切换文件、模式或关闭窗口时仍需验证待提交内容的归属和时序。

**原因**：内容经过块本地状态、父组件 blocks、全局 store 多层同步；全局保存直接读 store，没有统一提交屏障。现有 blur 和组件清理中的提交不能保证覆盖所有快捷键时序。

**解决方法**：

1. 提供按文档提交当前编辑状态的 `flushPendingEdits(documentId)` 接口，在保存、切换和关闭前等待提交完成。
2. 或将权威文档内容同步更新，仅对预览和昂贵计算防抖。
3. 待提交更新携带文档身份，防止旧文件内容提交到新的当前文件。
4. 配合 F02，以提交完成后的文档版本作为保存快照。

**验收标准**：输入后立即保存、300ms 内切换文件、关闭窗口、切换模式，最后输入均被保存或正确标记为未保存；不串写其他文档。需桌面端交互验证。

**代码位置**：[Block.tsx](../src/components/editor/blocks/Block.tsx) 的 `handleChange`、`handleBlur`；[wysiwyg-editor.tsx](../src/components/editor/wysiwyg-editor.tsx) 的同步 effects；[index.tsx](../src/components/editor/index.tsx) 的保存快捷键。

### F11：侧栏搜索未接入，全局搜索范围有限

**问题**：侧栏“搜索文件...”输入框没有过滤行为。全局搜索虽然已使用 Worker，但数据仅来自已加载的节点和内容：未展开目录中的文件不可见，未读取文件的正文为空。

**原因**：侧栏输入框没有绑定状态和事件；`buildSearchCorpus` 遍历内存树并使用 `node.content ?? ""`，没有磁盘搜索或完整索引。

**解决方法**：先接通侧栏过滤并保留匹配节点的祖先路径；明确标注“已加载文件”搜索范围。完整工作区搜索采用后台遍历或索引，支持取消、忽略目录和结果限制，并优先使用打开文档的未保存内容。

**验收标准**：侧栏输入能过滤、清空后恢复；如果标注为工作区搜索，未展开、未打开文件也可匹配，结果不会用磁盘旧内容覆盖草稿。

**代码位置**：[sidebar.tsx](../src/components/editor/sidebar.tsx)；[search-utils.ts](../src/lib/search-utils.ts) 的 `buildSearchCorpus`；[title-bar.tsx](../src/components/editor/title-bar.tsx)。

### F12：“展开全部”不加载未读取的子目录

**问题**：使用“展开全部”只展开已存在于内存中的目录节点，未读取目录可能显示为空，无法达到完整展开效果。

**原因**：该操作只递归设置 `isExpanded`，没有调用懒加载逻辑。

**解决方法**：将展开全部改为可取消的异步加载任务，限制并发和展开规模；复用稳定 ID 的目录合并逻辑。若只展开已加载节点，则修改菜单名称明确范围。

**验收标准**：多层未展开目录可以按约定展开；大目录不阻塞界面，失败和取消有反馈，草稿不受影响。

**代码位置**：[file-tree-context-menu.tsx](../src/components/editor/file-tree-context-menu.tsx) 的 `handleExpandAll`、`expandAllRecursive`。

### F13：路径身份和名称校验不完整

**问题**：同一文件使用不同分隔符、大小写或等价路径形式时可能无法去重。当前名称校验主要用于创建，重命名没有统一复用；另存为也未协调目标是否已被其他文档打开。

**原因**：`normalizeFilePath` 主要负责解析 `file://` URL，普通路径只做 trim；节点查找依赖字符串完全相等；用户输入直接参与路径拼接。

**解决方法**：

1. 将展示路径和文件身份键分离，在后端统一解析绝对路径与文件身份；大小写策略遵循实际平台／文件系统，不能全平台直接小写。
2. 校验文件名，处理 Windows 保留名称、分隔符、尾随空格／点和同名目标；创建、重命名和移动必须复用同一规则。
3. 新建目标尚不存在时根据父目录和合法文件名确定身份，不能只依赖对现有文件的 canonicalize。
4. 另存为已打开路径时明确合并或拒绝策略，避免同一个磁盘文件对应两个独立可写缓冲区。

**验收标准**：Windows 正反斜杠等价路径不重复打开；大小写敏感文件系统不错误合并文件；非法名称不会意外跨目录操作；同名目标不被静默覆盖。

**代码位置**：[editor-store.ts](../src/lib/editor-store.ts) 的 `normalizeFilePath`、`findNodeByPath`、`confirmRename`、`saveFileAs`；[file-operations.ts](../src/lib/file-operations.ts)。

### F14：保存与退出操作缺少完整交互闭环

**问题**：已有 `saveFileAs` 和部分文本格式过滤器，但未形成已有文件的显式另存为、全部保存和退出保存闭环。退出确认只有取消和确定关闭，用户确认后会直接放弃未保存内容。

**原因**：保存能力分散在多个 store action 和文件树按钮中，退出流程仅判断是否有未保存文件；保存函数没有返回明确结果供上层决策。

**解决方法**：补齐保存、另存为、全部保存入口；退出提供“保存并关闭／不保存／取消”。按实际文件类型设置保存格式，全部保存需汇总失败与取消结果。选择快捷键时避开现有 `Ctrl+Shift+S` 删除线绑定，统一调整并更新文档。

**验收标准**：多个草稿退出时可以逐个保存；任何保存失败或取消均不会误退出；TXT、JSON 等文本不会被强制改成 Markdown；PDF 不进入文本保存。

**代码位置**：[close-confirm-dialog.tsx](../src/components/editor/close-confirm-dialog.tsx)；[index.tsx](../src/components/editor/index.tsx)；[editor-store.ts](../src/lib/editor-store.ts) 的保存函数。

### F15：目录变化、文件失效和操作失败反馈不足

**问题**：外部新增、删除、重命名不会实时同步整个目录树；非当前文件的变化主要在再次打开时检查。读取失败可能回退到缓存或空内容，目录加载失败主要记录日志，用户难以区分空目录、无权限、文件已删除和加载失败。

**原因**：后端只维护一个当前文件 watcher，前端没有目录变更协调机制；部分异常被捕获后仅输出日志，没有明确的失效状态。

**解决方法**：

1. 对工作区根目录监听相关变化，合并高频事件并增量刷新；保留手动刷新作为补充。
2. 对原子替换、删除、重命名等不同事件分别处理，并验证监听能继续工作。
3. 文档与目录明确区分加载中、成功、失败、磁盘已删除和本地草稿状态。
4. 监听注册和清理处理异步竞态，兼容 React StrictMode；面向用户展示可重试的错误信息。

**验收标准**：在资源管理器中修改目录后树能同步；文件被删除时仍保留本地草稿并明确提示；权限错误不显示成空目录；快速切换文件不留下失效监听。

**代码位置**：[lib.rs](../src-tauri/src/lib.rs) 的 `watch_file_changes`；[index.tsx](../src/components/editor/index.tsx) 的 watcher effects；[file-operations.ts](../src/lib/file-operations.ts) 的 `loadFolderChildren`；[editor-store.ts](../src/lib/editor-store.ts) 的 `setActiveFile`。

## 4. 推荐修复顺序与回归范围

0. **恢复可验证基线**：先修复当前 `npm run build` 的类型错误和未使用变量；记录提交版本，建立保存竞态、路径身份、节点刷新和临时目录文件操作的最小自动化回归。
1. **先保护内容和保存协议**：F01、F02、F03、F08、F09、F10、F13。F08 与 F09 应通过同一个后端“版本未变化才写入”的保存协议实现。
2. **修复树与磁盘一致性**：F05、F04、F06、F07、F15。先稳定文档身份和路径，再接入真实移动、删除和目录监听；移动失败不能先更新内存树。
3. **补齐已有交互闭环**：F14、F11、F12。全部保存、退出保存和搜索等入口必须复用前面定义的操作结果。

回归至少覆盖：普通 Markdown、其他文本、PDF、无路径草稿；单文件与多层目录；保存中继续输入；目录刷新；外部修改／删除／重命名；同名目标；取消对话框；权限失败；Windows 路径；WYSIWYG 快速切换与立即保存。

验证文件操作时使用专用临时目录与样例文件。隔离测试用于检查调用和状态，桌面集成验证用于确认真实磁盘、系统对话框和文件监听行为，两者不能相互替代。每次阶段交付都应记录构建命令、提交版本和未覆盖的交互场景，避免把旧快照的验证结果当成当前基线。
