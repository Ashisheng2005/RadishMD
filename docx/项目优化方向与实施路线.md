# 项目优化方向与实施路线

初始分析日期：2026-09-22  
复核日期：2026-10-09  
分析对象：RadishMD 当前工作区源码  
状态：规划建议，已根据 2026-10-09 工作树复核，尚未完成实施

## 1. 优化目标与现有基础

目标是先让文件操作可靠，再提高连续写作、多文件管理和大目录使用体验。已确认的问题及修复方法见 [文件管理问题分析与修复建议](文件管理问题分析与修复建议.md)，其中 F01—F15 可作为后续任务编号。

当前已有目录懒加载、Markdown 渲染 Worker、搜索 Worker、两种编辑模式、外部修改检测和部分共用 Markdown 工具。工作树已有一批未提交的文件管理改动，包含 PDF 保存拦截、编辑版本、保存队列、真实目录创建和刷新时的部分 ID 保留。优化应建立在这些能力上，同时先清理当前构建错误，避免把部分修复重复实现。

当前 `npm run build` 尚未通过：`moveNode` 的声明返回 `Promise<void>` 但实现没有返回 Promise，`saveFileById` 还存在未使用变量。后续阶段的“完成”应以构建恢复绿色和对应回归通过为前提。

本文区分三类工作：

- **修复前置条件**：先解决文件损坏、内容丢失和树／磁盘不一致问题。
- **产品能力扩展**：补齐会话恢复、工作区搜索、批量操作、附件管理等能力。
- **架构与性能优化**：减少状态耦合、重复解析和不必要计算，建立可验证的质量基线。

## 3. 具体优化方案

### 3.1 文档与文件树状态解耦

**现状**：`FileNode` 同时保存目录关系、路径、内容、未保存状态、加载状态和展开状态。当前刷新逻辑已尝试按路径保留直接子节点 ID，但删除父目录时仍可能丢失 dirty 子孙；目录刷新和移除操作仍可能改变或丢弃编辑文档的身份。

**建议设计**：

- `WorkspaceNode`：磁盘条目与父子关系、加载／展开状态、对应文档引用。
- `DocumentBuffer`：稳定文档 ID、类型、路径身份、文本内容、编辑版本、已保存版本、外部磁盘版本、读写能力。
- `OpenDocuments`：已打开文档顺序、当前文档、每文档光标和滚动位置。
- `WorkspaceSession`：工作区根目录、布局、最近访问记录。

上述为概念划分，不要求立即拆成多个 Zustand store。先在单 store 中明确边界，也可以降低一次性迁移风险。

**关键约束**：目录刷新不重建文档 ID；未保存草稿不依赖目录节点存活；磁盘文件被删除时保留文档缓冲区并提示；路径去重与跨平台文件身份一致。树节点更新和文档缓冲区更新必须可以独立完成。

**验收目标**：刷新、移动、重命名、关闭目录均不丢失文档内容，当前文档引用始终有效。先完成 F03、F05、F13 的最小修复，再渐进拆分。

### 3.2 统一文件操作服务与保存协议

**现状**：多个保存函数重复写入、读取快照、更新状态和显示通知；部分操作有后端命令但未接通，结果没有统一返回格式。

**建议**：

1. 统一 `open`、`create`、`rename`、`move`、`save`、`saveAs`、`close`、`trash` 的应用层入口。
2. 操作返回明确结果，例如 `success`、`cancelled`、`conflict`、`error`，业务调用方据此决定是否继续。
3. 保存统一执行：提交编辑器内容 → 捕获版本 → 将期望磁盘版本传给后端 → 后端校验并原子写入 → 按版本更新状态。前端先检查再写入不能作为冲突保护。
4. 后端负责磁盘操作、平台路径、版本校验和原子写入，前端负责交互与文档状态；同文档保存串行化。
5. 统一错误信息，区分无权限、已删除、目标重名、路径不可用和格式不支持。

**收益**：全部保存、退出保存、自动保存都能复用可靠基础，减少每个入口重复修复。

**依赖**：F01、F02、F03、F08、F09、F10、F13、F14；F04、F06 应在保存协议稳定后接入。

### 3.3 草稿恢复、会话持久化与最近访问

**现状**：目前主要持久化 Tab 大小，没有工作区、打开文档或草稿恢复。正常退出确认不能处理崩溃和进程被终止。

**建议分步实施**：

1. 持久化最近文件、最近目录、主题、布局与打开文档列表。
2. 在应用数据目录保存草稿快照，包含文档 ID、路径、内容、编辑版本、时间和磁盘基准。
3. 启动时检测恢复记录，明确展示“恢复草稿／读取磁盘／另存副本”，不自动覆盖外部修改。
4. 可选自动保存应建立在版本化保存和冲突处理完成之后。
5. 草稿存储设置容量和清理策略，避免把大文档全部放入同步 `localStorage`。

**注意**：会话恢复、崩溃草稿恢复、自动写回原文件是三种不同能力，应分别定义和验证。

**验收目标**：强制结束进程后能恢复最近草稿；正常保存后正确清理恢复记录；原路径失效时仍可另存内容。

### 3.4 文件导航与完整工作区搜索

**现状**：已有基于 Worker 的搜索，但语料来自内存树。未展开目录和未读取正文不能完整参与搜索；侧栏搜索框未接入。

**建议**：

- 先提供可工作的树过滤，显示匹配文件及其祖先目录，明确“已加载文件”的范围。
- 工作区搜索在后台遍历或维护索引，支持取消、忽略目录、大文件限制与结果分页。
- 打开的未保存文档内容优先于磁盘内容，避免搜索结果与编辑区不一致。
- 分开提供快速打开文件、全文搜索和当前文档查找替换。
- 增加当前文件在树中定位、路径面包屑、键盘导航和明确的加载失败状态。

**验收目标**：未展开目录中的文件可以被工作区搜索命中；搜索不阻塞输入；取消旧查询后不会展示过期结果。

**依赖**：F05、F11、F12、F15。

### 3.5 批量操作与工作区管理

**现状**：没有完整的多选、复制文件、剪切粘贴、批量移动能力；真实目录与根级内存节点的操作语义需要明确。

**建议顺序**：

1. 真实文件复制、重命名、移动，统一同名冲突策略。
2. 多选与批量删除到回收站、批量移动、复制相对路径。
3. 明确添加工作区目录、关闭目录和永久删除目录的不同入口。
4. 为长任务提供进度、取消和部分失败结果；不能用一条成功提示掩盖部分失败。
5. 如果提供标签页或已打开文件列表，让关闭文档与磁盘树浏览相互独立。

**验收目标**：多选操作部分失败时，用户能准确知道哪些成功、哪些保留；取消不造成源文件丢失。

**依赖**：先修 F03、F06、F07、F13，再扩展批处理。F06 不能只复用当前 `moveNode` 的内存树操作，必须先完成后端移动、失败回滚和路径递归更新。

### 3.6 图片、附件与相对链接管理

**现状**：目录扩展名白名单过滤图片等附件。图片已支持路径解析，但缺少统一的资源管理流程。

**建议**：

- 提供 Markdown 优先视图和显示全部附件选项；不支持编辑的附件仍可定位或交给系统打开。
- 将粘贴／拖入图片保存到配置的资源目录，生成相对路径并处理重名。
- 无路径草稿先暂存资源，首次保存时明确迁移位置。
- 文件移动或另存到其他目录时提示相对链接影响，按选择调整引用或复制资源。
- 如增加未引用附件清理，先展示引用结果和待清理列表，不直接删除。

**验收目标**：文档及资源整体迁移后图片仍可显示；保存失败时资源与文档状态一致；图片同名不会覆盖已有资源。

### 3.7 文件类型、编码、换行与状态展示

**现状**：文档类型主要区分 Markdown 与 PDF，其他文本借用 Markdown 状态；读取使用 UTF-8，另存为固定 Markdown 过滤器，状态栏类型和编码文本也较固定。

**建议**：

1. 统一文件类型判断：Markdown、普通文本、PDF、其他附件，并按能力决定编辑器与保存方式。
2. 按类型选择保存扩展名和默认目录，避免不同打开入口产生不同模式。
3. 识别 BOM、保留 LF／CRLF；不支持的编码先明确提示，再按需求增加编码选择。
4. 状态栏展示真实类型、编码、换行方式和只读状态，允许复制完整路径。
5. PDF 的预览模式与用户的 Markdown 布局偏好分别保存。

**验收目标**：打开 TXT、JSON 和 Markdown 行为一致可预期；无实质编辑的保存不意外改变编码和换行；PDF 始终只读预览或二进制复制。

### 3.8 编辑器能力与写作体验

**现状**：分屏编辑实际使用原生 textarea，虽然依赖中已有 CodeMirror。WYSIWYG 使用块 textarea，尚无统一文档级撤销历史。

**建议**：

- 建立文档级撤销／重做，覆盖输入、工具栏格式化、块操作和任务勾选，避免切换模式后历史混乱。
- 为 WYSIWYG 提供按文档的待提交内容刷新接口；保存、切换文件、切换模式和关闭窗口必须等待刷新完成，再创建保存快照。
- 增加查找替换、每文件光标与选择区恢复、跳转行号、最近编辑位置。
- 评估是否接入 CodeMirror 6，以获得事务历史、选区管理、查找与大文档编辑能力；先做小范围验证，再决定迁移。
- WYSIWYG 优先验证中文输入法、快速保存、块切换、撤销及 Markdown 往返保真。
- 滚动同步从纯百分比逐步改善为源行／块锚点映射，重点验证图片、公式、图表造成高度变化的情况。
- 统一快捷键，处理重做快捷键与当前侧栏切换、另存为与删除线等绑定冲突。

**验收目标**：典型写作操作可以连续撤销恢复；中文输入不被快捷键或重渲染打断；模式切换不无故改变文档格式。

### 3.9 Markdown 解析一致性与安全渲染

**现状**：分屏与 WYSIWYG 保留两套解析实现，已有部分公共内联工具。链接地址直接拼接进 HTML 属性；WYSIWYG 的部分 Mermaid 错误／回退展示插入原内容，边界处理需要补齐。本次未验证完整可利用链。

**建议**：

1. 渐进提取共同语法层或中间结构，保留两种模式各自的渲染适配，不要求一次性重写。
2. 建立共享样例，覆盖嵌套列表、表格、代码围栏、转义、公式、图片和复杂链接。
3. 区分文本转义与 HTML 属性转义，为链接采用协议白名单，所有错误回退内容均转义。
4. 若支持原始 HTML，明确可信边界并采用合适的 HTML 清洗策略；CSP 不能替代正确的输出处理。
5. WYSIWYG 记录源文本信息，减少重新序列化时不必要的格式变化。

**验收目标**：同一输入在两种模式下语义一致；格式异常或含特殊字符的链接、Mermaid 源码不能插入非预期 HTML；不修改内容的模式切换保持文本稳定。

### 3.10 状态更新、搜索和大文档性能

**现状**：多个组件直接订阅整个 store，包括文件树条目；内容变更会更新树并触发无关组件。搜索语料按 files 变化整体构建和传输，字数统计也有重复计算路径。

**建议**：

- 使用精确 Zustand selector 和稳定 action 引用，避免输入时整棵树跟随更新。
- 文档内容独立存储，只通知当前编辑器、必要状态栏和当前文档索引。
- 搜索 Worker 改用单文件增量更新，合并连续输入产生的索引任务。
- 字数统计集中管理，按需求节流，避免同步与延迟逻辑重复扫描。
- 大目录使用虚拟列表；大文件设置加载提示和必要的轻量模式。
- 对 KaTeX、Mermaid 和 PDF 等按需加载，先测量包体和启动收益再调整。
- 控制生产环境逐次编辑日志，使用可开关的诊断日志记录操作结果。

**测量方法**：分别使用日常文档、大文档、多文件目录、含大量图表的文档，记录输入响应、切换延迟、搜索耗时、首次渲染和内存。确定基线与目标后再实施，不把“使用 Worker”直接等同于性能问题已解决。

### 3.11 测试、CI、可访问性与文档维护

**现状**：无测试基础；当前 CI 主要构建前端，Rust 检查仍被注释。项目说明中关于 CodeMirror、目录行为和后端命令数量的描述与实际代码存在差异。

**建议**：

1. 优先为保存竞态、节点身份、路径去重、未保存保护和解析一致性建立自动化回归；先修复当前构建错误，再把 `npm run build` 作为每阶段的硬门槛。
2. 后端使用临时目录验证创建、移动、写入失败、原子替换和重名保护；关键桌面流程增加集成验证。
3. CI 使用锁文件安装依赖，恢复 Rust 检查并安装完整平台依赖；当前工作流中的 Rust 检查仍被注释，至少持续验证主要目标平台。
4. 为文件树提供清晰焦点、键盘操作、可访问名称；为图标按钮补齐说明和合理的状态反馈。
5. 更新 AGENTS、开发者手册和使用手册，明确实际实现、快捷键及浏览器预览与 Tauri 的能力差别。

**验收目标**：F01—F06 等核心缺陷修复后有可重复回归；CI 能发现前后端编译问题；文档与实际入口保持一致。

## 4. 推荐实施路线

### 第零阶段：恢复可验证基线

范围：修复当前 TypeScript 构建错误；记录工作树提交版本；建立保存竞态、路径身份、目录刷新和专用临时目录文件操作的最小回归。

交付：`npm run build` 通过，核心回归可以重复执行，文档中的验证结果与当前提交一致。

### 第一阶段：文件操作可靠性

范围：修复 PDF 保存、保存竞态、未保存移除闭环、文档身份、外部冲突、原子保存、路径校验和 WYSIWYG 提交屏障。

交付：核心文件操作不损坏内容；保存失败、冲突和取消都有明确结果；树与文档缓冲区的生命周期可以分离。此阶段不以新增菜单数量作为完成标准。

### 第二阶段：保存闭环与工作连续性

范围：真实目录创建与移动、删除范围和目录监听、另存为和全部保存、退出保存、草稿恢复、最近访问、基础搜索和真实文件类型展示。原子保存和冲突处理应在第一阶段完成，不能延后到本阶段。

交付：保存失败可处理、意外退出可恢复、目录变化可感知、搜索范围明确。完整工作区搜索可以按数据规模分步交付。

### 第三阶段：多文件效率与写作体验

范围：多选、复制粘贴、批量移动、完整工作区搜索、附件管理、编码与换行支持、编辑历史与查找替换。

交付：跨目录整理和长时间写作有完整操作闭环；批量操作支持进度、取消和失败结果。

### 持续工作：架构、性能和质量

随上述阶段逐步拆分文档与树状态、收敛 Markdown 解析、完善渲染边界、增量搜索、精确订阅和 CI。性能优化由测量结果驱动，不等到全部功能完成才开始回归验证。

## 5. 范围控制建议

- 优先复用当前 Tauri、React、Zustand 与 Worker 基础；框架更换不是文件管理问题的前置条件。
- 会话恢复先保证草稿可靠，不急于引入云同步、多端协作等扩大一致性复杂度的能力。
- 先明确真实目录、无路径草稿和虚拟分组的产品语义，再扩展工作区和批量操作。
- 每阶段以可复现的用户场景与验收结果结束，后续可将对应问题编号拆成独立任务。
- 以当前构建通过、回归结果可追溯为阶段门槛；不要把旧工作树上的“tsc 通过”记录直接沿用到新提交。
